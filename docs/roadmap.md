# Фичи, задачи и Git Flow

## Исходное состояние

Проверено 28 октября 2026 года: в репозитории есть только начальный README,
ветка `main` и GitHub remote `amedvedevx/tetris-oop`. Исходников, конфигурации
сборки, зависимостей, тестов и CI нет. Рабочее дерево до проектирования чистое.
`AGENTS.md` в каталоге проекта и родительских каталогах отсутствовал.

Поэтому сейчас невозможно провести ревью существующих игровых алгоритмов или
оценить их покрытие. Первый результат — проект и перечень рисков. Глубокое ревью
реализации проводится перед тестированием каждой появившейся фичи; общее ревью
всего приложения — после их сборки.

## Порядок работы

Одна задача — одна рабочая ветка и один PR. Задача реализации фичи и задача её
покрытия идут последовательно, с отдельным пользовательским ревью каждой.
Внедрять следующую фичу до принятия тестов предыдущей не планируем. UI создаём
по [компонентной архитектуре](ui-architecture.md): сначала базовые компоненты
в корневой `/components`, затем блоки и страница; для каждого применяется
`ui-refactoring` и создаётся собственная история Storybook.

В паре `06 → 07` первая задача — реализация, вторая — отдельное покрытие тестами.
Если обнаруженный дефект требует отдельного исправления, создаётся дополнительная
задача `fix` и PR. Это не скрывается внутри несвязанной тестовой задачи.

Приращения зависят от предыдущих: F04 добавляет базовый проигрыш, F05 выполняет
падения, а F07 подключает к ним начисление очков. Полные правила описывают целевую
версию; в каждом промежуточном PR перечисляются уже доступные сценарии.

## Ветки

- `main` — принятые релизы.
- `develop` — принятые задачи текущей версии; создаётся от исходного `main`.
- `codex/docs/001-project-design` — текущая первая задача, PR в `develop`.
- `codex/feat/002-ui-foundations` — пример ветки реализации.
- `codex/test/003-ui-foundations` — пример следующей отдельной тестовой задачи.
- `codex/fix/<task>-<description>` — багфикс в `develop`.
- `codex/refactor/<task>-<description>` — самостоятельный рефакторинг.
- `codex/release/1.0.0` — релиз от `develop`, PR в `main`; релизные изменения
  затем возвращаются в `develop` отдельным PR, если они есть.
- `codex/hotfix/<task>-<description>` — только срочное исправление принятого релиза,
  от `main`, с переносом в `develop` после ревью.

Это Git Flow с префиксом рабочих веток `codex/`. На GitHub merge request
называется pull request; в этом проекте используем PR.

## Завершение задачи

1. Проверить актуальную базу и создать ветку от `develop`.
2. Выполнить только текущую задачу, обновить нужную документацию.
3. Для тестовой задачи выполнить процесс с двумя саб-агентами из
   [testing.md](testing.md), исправить найденные проблемы.
4. Запустить относящиеся к изменению проверки. Не выдавать запланированные
   сценарии за выполненные.
5. Сделать commit и push. Создать PR с проблемой, результатом, проверками,
   ограничениями и ссылкой на отчёт ревью для тестов.
6. Передать PR пользователю. Замечания и рефакторинг текущей задачи вести
   в этом PR, повторяя затронутые проверки.
7. Дождаться принятия. Merge — по указанию пользователя либо самим пользователем.
   Просьба принять задачу и перейти дальше разрешает её merge. Автослияние выключено.
8. Начать следующую задачу от обновлённого `develop`.

Коммит сам по себе не завершает задачу. Независимое ревью саб-агента не заменяет
пользовательское ревью. `/goal` продолжает общую цель в пределах этих правил
и не разрешает обходить остановку после каждого PR.
