# F01: надёжные тесты новой партии и очереди

Задача №07, ветка `codex/test/007-new-game-and-queue`, принятая база
`16f8bda60cfa6e211dcb3bd0e275ec74f445f65f` (merge PR №6).
UI, components/ и production src/ не изменяются. Ожидания основаны на
[правилах игры](../game-rules.md), объём — F01 из [плана](../roadmap.md).

## Ревью реализации до тестов

Изучены все модели domain, контроллер, адаптер и GameView, bootstrap, компоненты,
существующие проверки, Vite/Playwright/Vitest и CI. Основные риски: ошибочные
spawn-матрицы и смещение, расходование очереди при чтении, продолжение старого
мешка на restart, потеря рекорда в ответе контроллера, утечки вложенных массивов
и точек, общий state экземпляров, частичная публикация неуспешного нового state,
двойной restart и отсутствие реального подключения в обычном main.ts.

Текущая реализация поддерживает только ready/running и start/restart. Поле
закреплённых клеток пока всегда пустое, результаты равны 0/0/1. Поэтому тесты
не конструируют недостижимое занятое поле через private-поля и не выдают
сохранение нулевых значений за доказательство сброса ненулевого результата.

## Обсуждение до написания тестов

Первый агент `/root/f01_test_scenarios` — gpt-6-astra, high,
fork_turns none. Он независимо прочитал код и спецификации. Матрица A–F явно
согласована агентом, затем подтверждена ведущим до создания первого теста.

Содержательные разногласия и уточнения:

1. Бесконечно повторяющийся второй мешок может скрыть двойной restart. Согласован
   конечный источник с четырьмя различающимися парами I/O → L/O → J/O → Z/O;
   лишний расход либо меняет ожидаемый результат, либо явно исчерпывает источник.
2. Ведущий нашёл контрпример собственному исходному I/O → O/T: такая пара после
   restart получится и при продолжении старой очереди. Поэтому второй мешок
   начинается с L, а счётчик RNG только дополняет поведенческий oracle.
3. Одна перестановка первого типа дала бы следующий O почти во всех семи случаях.
   Вместо этого согласованы семь циклических перестановок с парами I/O, O/T,
   T/S, S/Z, Z/J, J/L, L/I: каждый тип проверяется как активный и как preview.
   Агент независимо проверил шесть буквальных RNG-входов каждой перестановки
   обратным разбором. Обратного алгоритма перемешивания в тестовом oracle нет.
4. Агент уточнил верхнюю границу double: настоящий сосед 1 снизу —
   1 - Number.EPSILON / 2, а не 1 - Number.EPSILON. Используется literal
   0.9999999999999999 вместе с нижней границей 0.
5. Одного равенства старого снимка после restart недостаточно: заменённый Board
   скроет прежнюю утечку. Мутируются возвращённые строки/внешний массив и точки
   активной фигуры; тот же session читается до restart, затем старые данные
   мутируются ещё раз после restart и проверяется другой session.
6. Тестовый bootstrap может пройти при сломанном обычном entry. Поэтому кроме
   контролируемых сценариев есть полный текущий поток через обычный production
   main.ts. Наблюдённый тип лишь выбирает буквальный oracle для его геометрии.
7. Все семь типов не умножаются на ввод и viewport: их покрывает реальная
   интеграционная цепочка, браузер проверяет три ширины и настоящие действия.
   Поздние отказы источника проверяются в ready и running, потому что атомарность
   уже заявлена документацией реализации.

`tests/integration/new-game.test.ts` добавляет 12 интеграционных случаев;

## Тестовый вход и обычная сборка

HTML/main/Vite-конфигурация в tests/fixtures/new-game/ создают те же Session,
Controller и GameView с той же темой; различается только RandomSource. Никакого
объекта ядра на window, query-переключателей поведения или загрузки поля нет.
build:e2e использует общую Vite/Tailwind-конфигурацию, но отдельный HTML input
и output .cache/e2e-app/. Playwright поднимает третий изолированный static server
на 4181; обычный dist остаётся на 4180, Storybook — на 6106. Существующие серверы
не переиспользуются, раннер останавливает все три.

Проверка сборки находит только index.html в обычном dist и отсутствие test-title
и строки отказа конечного источника в HTML/JS. Controlled HTML при этом существует
в отдельном output. Стандартный production-поток использует настоящий
MathRandomSource; каждый наблюдённый тип проверяется по полному literal-рисунку,
а первые active/next различаются как два элемента одного мешка. Это проверка
допустимых результатов, не статистическая оценка распределения.

## Проверки чувствительности

Сначала прошли baseline Vitest и обычный production-поток. Временные дефекты
вносились последовательно; для браузерных случаев пересобирался нужный output.
Все 11 случаев дали assertion failure ровно одного выбранного теста, без
зачёта ошибки сборки или пустого выбора. Восстановление выполнялось в finally.

| Дефект | Фактический провал |
| --- | --- |
| Spawn x+4 вместо x+3 | Literal координаты I не совпадают |
| Последняя клетка O смещена | Literal координаты O не совпадают |
| Peek удаляет следующий элемент | Повторное чтение даёт O вместо I |
| Restart продолжает старую очередь | O вместо нового L |
| Ответ restart теряет рекорд | UI показывает 0 вместо 9800 |
| Snapshot копирует только внешний board-массив | Изменённая строка видна в следующем snapshot |
| Активная фигура отдаёт кэш массива точек | После мутации уже пять неверных точек вместо четырёх исходных |
| Start в running создаёт новую партию | L вместо сохранённого I |
| Active очищается до успешного shuffle | После отказа ready вместо сохранённого running |
| Controller дважды выполняет restart | Controlled browser получает J вместо ожидаемого L |
| Обычный bootstrap не доставляет click | Production status остаётся ready вместо running |

Manifest с точными подменами, runner и логи — .cache/007-mutants/.
restored=true подтверждён; `git diff --exit-code -- src components` завершился
успешно. Затем выполнен полный финальный check с нормальными тремя сборками.

## Ограничения

Занятое закреплённое поле и ненулевой счёт недостижимы через текущие команды:
их сброс не объявляется проверенным. Движение, повороты, гравитация, закрепление,
строки, начисление очков, пауза, проигрыш и persistent record — следующие задачи.
Только Chromium; Firefox/WebKit, screen reader и нативный text zoom не проверены.
Root-font проверки прежнего набора не называются нативным zoom. Фигуры/матрицы
проверяются детерминированно, качество реального RNG статистически не оценивается.
Принятие этого PR остаётся пользовательским шагом; задача №08 до него не начинается.
