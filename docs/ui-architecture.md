# UI: Tailwind и компоненты

Статус: шесть примитивов и их тесты приняты; в задаче №04 добавлены составные
блоки и статическая GamePage. Игрового ядра пока нет. Базовые API —
в [components.md](components.md), контракты блоков и результаты проверки —
в [game-shell.md](game-shell.md).

## Основа и порядок

TypeScript + Vite, DOM-компоненты, Tailwind CSS и Storybook для HTML/Vite.
Компоненты реализуются функциями с типизированными параметрами и DOM-результатом;
игровое ядро и его ООП-модели остаются независимыми от UI.

Перед созданием или изменением **каждого компонента, блока и страницы** обязательно
применяется навык `ui-refactoring`, явно указанный пользователем. Его требования
к инкапсуляции, плоской библиотеке, Wrapper, историям и отчёту применяются
также при создании нового UI. На старте проекта прежнего UI не было. Последующие
изменения должны сохранять согласованное поведение и внешний вид, если
пользователь не просит их изменить.

Порядок: общие токены и инструменты → базовые компоненты с историями → блоки
из этих компонентов с историями → GamePage как композиция блоков.
В каждой следующей фиче недостающий компонент сначала создаётся и проверяется
отдельно, затем включается в блок и страницу. Не создавать неиспользуемые заглушки
всего будущего каталога заранее.

Все собственные UI-компоненты находятся **плоско в `/components` в корне проекта**.
Там же лежат `*.stories.ts` и связанные стили. Блоки и GamePage — тоже компоненты
этой библиотеки. `src/main.ts` создаёт приложение, `src/presentation/GameView.ts`
связывает состояние и события; они не объявляют локальные стилизованные блоки.

## Начальный каталог

| Порядок | Компоненты | Ответственность |
| --- | --- | --- |
| 1 | `Typography`, `Wrapper` | Весь видимый текст и внешний адаптивный layout |
| 2 | `Button`, `Surface`, `BoardCell`, `KeyHint` | Действия, поверхность панели, клетка поля и подсказка клавиши |
| 3 | `StatItem`, `NextPiecePreview`, `GameBoard` | Показатель, следующая фигура и поле из клеток |
| 4 | `GameStats`, `GameControls`, `GameStatus` | Панель показателей, действия/подсказки и состояние партии |
| 5 | `GamePage` | Композиция готовых блоков для текущей стадии приложения |

Перечисленные компоненты реализованы. Дополнительно выделены GameHeader
и изолированные интерактивные примеры библиотеки. Данные и действия добавляются
в блоки по мере реализации соответствующих игровых фич. Для каждого перечисленного
компонента нужна собственная история; история страницы не заменяет истории детей.

## Владелец стилей и закрытый API

Tailwind utility-классы находятся внутри реализации владельца. Потребитель
передаёт данные, содержимое, обработчики, доступность и ограниченные семантические
режимы, например `variant`, `size`, `tone`, `disabled`, `fullWidth`.

Публичных `className`, `class`, `style`, `css`, `sx`, `classes`, `containerStyle`,
overrides и произвольных CSS-переменных нет. Широкий DOM props/rest-проброс
не должен возвращать эти поля. Атрибуты `aria-*`, `data-*`, события и ref
передаются только через контролируемый контракт.

Внутри `Button` находятся высота, внутренние отступы, фон, рамка и состояния
hover/focus/disabled. Внешний отступ до соседнего блока задаёт `Wrapper`.
`Surface` владеет фоном, рамкой и внутренним отступом панели. Составной блок
владеет своим внутренним layout; пользователь блока не настраивает его интервалы.

Нельзя менять потомков через родительские селекторы, `!important`, инъекцию
классов/пропсов, глобальные overrides или произвольные темы. Обёртка не превращается
в способ перекрасить, обрезать или масштабировать дочерний компонент.

## Typography

Весь видимый текст приложения создаётся через `Typography`: заголовок, подписи,
инструкции, значения счёта/уровня/рекорда, кнопки, состояния и сообщения.
Компоненты со строковыми параметрами, например `Button({ label })`, сами создают
для этой строки `Typography`. Это правило действует и для демонстрационных
страниц/историй, которые мы пишем; служебный интерфейс самого Storybook не меняем.

Минимальный контракт:

- `as` — ограниченный набор семантических тегов: `h1`, `h2`, `h3`, `p`, `span`.
  Он отвечает за HTML-семантику, а не за внешний размер.
- `variant` — `title`, `heading`, `body`, `caption`, `label`, `metric`.
- `tone` — ограниченные осмысленные роли текста из общей темы.
- `text` — строка или число; безопасное создание текста через `textContent`.
- Нужные атрибуты доступности и идентификатор без CSS-каналов.

Для текста внутри кнопки или `kbd` используется `span`, для заголовков — нужный
уровень `h1`–`h3`. Не вставлять абзац или заголовок внутрь кнопки. Дополнительный
тег вводится только при реальной семантической потребности. Документный `<title>`
и невидимые значения `aria-label` не являются визуальными текстовыми узлами;
их строки не оборачиваются DOM-компонентом.

Размер, межстрочный интервал, насыщенность и адаптивные переходы каждого варианта
заданы внутри `Typography` через общие токены. Страница не назначает `text-*`,
`font-*` или `leading-*` дочернему тексту. Нет произвольных `fontSize`, `lineHeight`
и карты CSS в публичном API. Текст переносится; длинные значения не прячутся
фиксированной высотой или обрезкой. Числовые показатели используют табличные цифры.

## Wrapper и адаптивность

`Wrapper` — единственное целевое исключение для публичных layout-пропсов:
направление, промежуток, внешний отступ, собственный padding обёртки,
выравнивание, ограничение колонки и размещение в flex/grid. Значения ограничены
шкалами и конечными режимами проекта; произвольного CSS-объекта нет.

Адаптивные значения задаются типизированными ключами `base`, `sm`, `md`, `lg`
и переводятся внутри Wrapper в полные Tailwind-классы. Эти ключи используют общие
breakpoint-токены, а не локальные числа в каждом блоке. `dir` обрабатывается
компонентом и не попадает в HTML как направление текста.

Базовый layout рассчитан на узкий экран: поле и панели идут последовательно.
На широкой области блоки располагаются рядом. Клетки поля остаются квадратными,
соотношение сторон внутренней сетки — 1:2; изменение ширины не меняет число клеток
и правила. Видимая рамка входит во внешний размер GameBoard, а не рисуется снаружи.
`GameBoard` владеет своей сеткой, а Wrapper — занимаемым им местом в странице.
В двухколоночной странице поле и статус имеют общий предел ширины board;
статус и управление выровнены снизу, расположенные рядом показатели и preview —
по высоте. Это раскладка по содержимому через Wrapper, без фиксированных высот.
Общий токен --container-board включает рамку; внутренние размеры клеток определяет
GameBoard. Мини-поле preview центрируется по горизонтали через внутренний Wrapper,
а заголовок и пояснение сохраняют выравнивание по левому краю.

Не уменьшать весь UI через `transform: scale`, не прятать переполнение вместо
исправления layout и не блокировать увеличение текста. При ширинах 320, 768
и 1280 CSS px проверяются читаемость, переносы, доступность кнопок и отсутствие
горизонтальной прокрутки страницы. При увеличении текста до 200% содержимое
остаётся доступным; вертикальная прокрутка на коротком экране допустима.

## Tailwind и Storybook

Tailwind подключается через Vite-плагин. Общий `components/theme.css` содержит
entry point Tailwind и дизайн-токены: цвета ролей, шрифты, расстояния, радиусы
и breakpoint-значения. Он не содержит правил, дооформляющих конкретные компоненты
снаружи. Базовый reset Tailwind допускается, оформление задают компоненты.

Семантические варианты переводятся в **полные статические имена классов** внутри
компонентов. Нельзя собирать Tailwind-классы из фрагментов вроде `bg-${tone}-500`:
сканер сборки должен обнаруживать все варианты. При необходимости явно включить
корневую `components/` в источники сканирования.

Приложение и Storybook используют одну тему, обработку Tailwind и компоненты.
Истории лежат рядом с компонентами, используют только разрешённый API и Wrapper
для размещения, локальные данные и обработчики без бизнес-побочных эффектов.
Controls не раскрывают запрещённые overrides.

Для каждого компонента показываются применимые варианты/размеры, disabled,
пустые/заполненные значения, длинный текст и узкий viewport. Для GameStatus
показываются только реально поддерживаемые состояния текущей стадии. Focus
и клавиатурное поведение проверяются на настоящих HTML-элементах.

## Приёмка каждого компонента, блока и страницы

1. Проверить существующий каталог и применить `ui-refactoring`.
2. Завершить файл вместе с API, нужными зависимостями, потребителями и его story.
3. Проверить типы, lint, сборку приложения и Storybook; открыть и посмотреть
   значимые состояния и ширины. Наличие файла story само по себе не доказывает,
   что компонент отображается правильно.
4. Проверить, что внешний код не управляет косметикой, а весь видимый текст
   проходит через Typography. Проверить HTML-семантику и сохранение фокуса
   при обновлении снимка игры.
5. Дать пофайловый отчёт навыка: что было, что перенесено внутрь, что добавлено,
   что удалено из API, какая граница появилась, какие истории и проверки выполнены.
   Для нового файла отметить отсутствие прежней реализации и удалённых overrides.

Автотесты добавляются отдельными задачами по согласованному процессу с обсуждением
сценариев и независимым ревью. Ручной просмотр, история Storybook и успешная сборка
не называются автоматическим покрытием. До появления UI визуальные проверки
и Storybook ещё не выполнены для будущих блоков и страницы; результаты для
базовых компонентов фиксируются отдельно.

## Обновление данных статической страницы

GamePage остаётся DOM-фабрикой, но возвращаемый элемент имеет ограниченный метод
`update(GameScreenData)`. GameControls и GameStatus аналогично обновляют свои данные.
Это не игровой цикл и не переходы игровой модели: компонент получает готовый снимок,
публикует действие через callback и сам не решает исход команды.

При обновлении заменяются поле, показатели и preview. Контролы, нативные кнопки
и live-region статуса остаются на месте. Button.setLabel обновляет только видимую
подпись через существующий Typography; тип, события, оформление и явный ariaLabel
сохраняются. Поле и preview проверяют размеры своих представлений до вставки.

GameScreenData — типы слоя представления. Будущее ядро не должно импортировать UI;
его снимок преобразуется в эти данные в presentation. Storybook-пример переключает
заданные fixtures, не входит в entry point приложения и не является движком.
